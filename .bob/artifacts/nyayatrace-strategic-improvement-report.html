Product Strategy Report

NyayaTrace — Strategic Improvement Analysis

10 prioritized recommendations to make NyayaTrace production-ready, innovative, and visually compelling
Stack: Next.js 14 · Drizzle ORM · SQLite · Framer Motion · Tesseract.js · Gemini / OpenAI
Domain: Indian criminal law case management (bail, parole, document verification)
Purpose: Local legal-record workspace for advocates and clerks

Executive Summary

NyayaTrace is a well-architected, domain-specific legal workspace with genuine differentiators: a three-panel resizable verification workspace, statutory bail countdown logic (CrPC/BNSS auto-detection), an IPC↔BNS concordance matrix, AI-grounded analysis (Gemini/OpenAI), and court-quality document export. The core technical foundation is solid. The gap between "impressive prototype" and "production-grade tool" lies primarily in four areas: real authentication and multi-user safety, workflow automation that reduces manual repetition, richer data visualization and timeline storytelling, and making AI capabilities more discoverable and interactive. The recommendations below address those gaps without recommending complexity for its own sake.

Three Strongest Opportunities
🏆 #1 Must-Have
Real Authentication & Role-Based Access
The current localStorage-only auth is a single critical blocker for any real deployment or team usage.
🚀 #2 High Impact
Interactive Case Timeline Visualization
A scrollable, zoomable SVG/canvas timeline linking hearings, orders, bail deadlines, and compliance events is the missing "aha moment".
💡 #3 Differentiator
AI-Powered Draft Application Generator
Automatically drafting bail applications from case data + verified findings closes the loop from "research tool" to "filing tool".
All 10 Recommendations — Ranked by Value & Feasibility
1

Real Server-Side Authentication & Role-Based Access Control

Replace localStorage session with JWT / session cookies; add Advocate vs. Clerk vs. Admin roles
Must-Have Medium Complexity
Problem
Auth is entirely client-side localStorage. Any user who opens DevTools can impersonate any user. SignUp creates an account that persists nowhere on the server. This is the single biggest blocker for real-world deployment or team demos.
Proposed Implementation
Add a users table to the SQLite schema (hashed passwords via bcrypt). Add a sessions table or use signed JWT HttpOnly cookies. Wrap all /api/* routes and page layouts in a server-side auth check using Next.js middleware. Add three roles: Advocate (full access), Clerk (read-only reports/hearings), Admin (user management). Guard case deletion and AI analysis trigger by role.
User Benefit
Teams can share the same NyayaTrace instance. The audit log (already in the schema) becomes meaningful — events are attributed to real authenticated users, not "performed_by: string".
Tech Required
bcryptjs jose (JWT) Next.js middleware.ts Drizzle users + sessions tables
Expected Impact
Transforms the project from "single-user prototype" to "team-deployable application". Directly unlocks audit trail credibility.
2

Interactive Unified Case Timeline (SVG / Canvas)

A single scrollable timeline merging hearings, judicial orders, bail deadlines, custody clock, and compliance events
High-Value Medium Complexity
Problem
Case chronology currently lives in three separate places: HearingTimeline in Case Progress, TemporalTimeline in Verification, and MasterChronologyView in Case Progress. These are disconnected views that require tab-switching to get the full picture. The bail countdown and compliance events are never shown alongside hearing history.
Proposed Implementation
Build a new UnifiedCaseTimeline component using a lightweight SVG or d3-style layout. Plot all events on a single horizontal axis: arrest → remand → hearings → orders → bail deadline → parole end. Use color-coded lanes (judicial=blue, statutory=amber, compliance=emerald). Enable hover tooltips showing full event detail. Add a zoom slider (1 month → full case span). Expose this in the Case Workspace, Case Progress, and as a full-screen overlay from a keyboard shortcut.
User Benefit
An advocate can see the entire procedural history of a case in one glance. The relationship between a delayed chargesheet and an upcoming bail deadline becomes visually self-evident.
Tech Required
d3 (scale/axis only) SVG rendering in React No new DB tables — queries existing hearings + orders + bailConditions
Expected Impact
The single most visually impressive feature for a demo. Makes the app's purpose immediately legible to any new user.
3

AI-Powered Bail Application Draft Generator

Use verified findings + statutory bail calculations to auto-draft a structured bail application, editable before export
High-Value Medium Complexity
Problem
The DraftApplicationTab exists in Bail Briefs but appears to be a static template. The verified findings, statutory bail status, hearing chronology, and surety bond data are all already in the DB — but none of them are automatically composed into a draft application. The user must manually write this from scratch or use the generic Word export (which is a fixed HTML template).
Proposed Implementation
Add a POST /api/cases/[id]/bail-draft/generate endpoint. Feed it: statutory bail status, all verified findings with source citations, hearing list, surety bonds, and parole timeline. If Gemini/OpenAI is configured, use AI to generate natural-language paragraphs. If not, use a deterministic template engine (the way wordExport.ts already works). Render the draft in a rich-text editor (e.g. tiptap) so the advocate can edit, add signature blocks, and then export to PDF or DOCX.
User Benefit
An advocate can go from "documents uploaded" to "draft application ready for review" in minutes. This closes the workflow loop that currently ends at "here are your findings".
Tech Required
tiptap (rich text editor) Gemini / local template fallback No new DB schema (uses existing tables) Enhanced word export
Expected Impact
Converts NyayaTrace from a case-management tool into an end-to-end filing assistant. Strongest portfolio/hackathon differentiator.
4

Contextual AI Chat ("Ask About This Case")

A sidebar RAG chat that answers questions grounded in the case's own extracted document text
High-Value High Complexity
Problem
The AI analysis today is a one-shot batch operation. There is no way to ask follow-up questions like "What does the panchnama say about the date?" or "Which witnesses gave contradictory statements on location?". Users must re-read raw page text manually.
Proposed Implementation
Add a collapsible chat drawer to the Verification Workspace. Each chat message is sent with the extracted page text of the current case (already in the DB) as context. Use the same Gemini/OpenAI integration already present. Enforce the existing grounding rule: AI responses must cite a documentId + pageNumber. Display cited passages as inline quote cards. Store conversation threads per case in a new case_chats table (optional — can be session-only first).
User Benefit
Dramatically reduces the time to find a specific fact in large document sets. Makes the AI feel like a knowledgeable assistant rather than a one-click button.
Tech Required
Gemini or OpenAI (already integrated) Streaming API response (SSE) Optional: case_chats table External API key required
Expected Impact
Highest wow factor for a live demo. Demonstrates responsible AI use (grounded, not generative).
5

Real-Time Statutory Bail Alert & Notification System

Persistent urgency alerts when bail deadlines are ≤10 days away, surfaced on the dashboard and in a dedicated notification center
Must-Have Low Complexity
Problem
The statutory bail countdown logic (calculateStatutoryBail) correctly identifies "urgent" and "accrued" cases. However, this information is only visible if the user navigates to the Bail & Parole section. There is no proactive alert surface. A missed bail deadline has irreversible consequences for an accused — this is the highest-stakes data in the app.
Proposed Implementation
Extend the existing UrgencyTicker component and the dashboard's urgency logic. Add a bell icon in the Topbar that shows a badge count. Clicking it opens a notification panel listing all urgent/accrued cases. Persist a "dismissed" flag per case per day in localStorage (or a DB table). Add an animated pulsing ring on the Sidebar "Bail & Parole" nav item when urgent cases exist. On the Overview dashboard, make the urgency cards link directly to /bail-briefs/[id].
User Benefit
The system proactively tells advocates what needs immediate action, rather than requiring them to check every case. Directly prevents a high-stakes procedural miss.
Tech Required
Topbar notification bell (UI only) calculateStatutoryBail (already exists) No new DB tables needed
Expected Impact
Highest safety impact. Low effort relative to value. Makes the existing bail logic far more discoverable.
6

Full-Text Search Across All Document Pages

Add SQLite FTS5 full-text search so users can search any extracted word across all documents in all cases
High-Value Low Complexity
Problem
There is a /api/search route and a CommandPalette, but search appears to cover case numbers and titles only. The pages table contains extracted text for every document page — yet there is no way to search "What cases mention Randhir Singh?" or "Find all pages with the word 'alibi' across all cases". This is the most valuable search capability for a legal research tool.
Proposed Implementation
Add an SQLite FTS5 virtual table (CREATE VIRTUAL TABLE pages_fts USING fts5(extracted_text, content=pages)) via a new migration. Extend the /api/search route to query this table. Surface results in the CommandPalette with document and page number, showing a 120-character snippet with the match highlighted. Clicking a result navigates to /verification/[caseId] and pre-selects the document and page.
User Benefit
Transforms the CommandPalette from a navigation tool into a research tool. "Find anything, anywhere, instantly" is a compelling capability that saves hours of manual page-by-page scanning.
Tech Required
SQLite FTS5 (built-in, no extra dep) New migration script Enhanced /api/search route CommandPalette UI update
Expected Impact
Highest ROI improvement. SQLite FTS5 is already available — this is almost entirely a query and UI task, not infrastructure work.
7

Document Processing Status & OCR Quality Dashboard

A visual per-document quality map showing which pages extracted poorly, with a one-click re-OCR trigger
High-Value Low Complexity
Problem
Pages have a quality field ('good' / 'poor' / 'unreadable') and the README warns that OCR output must be manually checked. However, there is no visual surface that shows which pages of which document are poor quality. Users discover this only when they happen to read a page. Poor-quality pages silently degrade AI analysis accuracy.
Proposed Implementation
In the DocumentPanel, add a miniature page quality bar below each document name — a row of small colored squares (green=good, amber=poor, red=unreadable) corresponding to each page. Hovering a square shows the page number. Clicking a poor/unreadable square opens the viewer on that page. Add a "Re-process page" button (calls a new API route) for individual pages that failed OCR. Show an aggregate quality score ("12/15 pages good") for each document.
User Benefit
Users can immediately see OCR completeness without opening every page. Re-processing bad pages without re-uploading the entire document saves significant manual work.
Tech Required
No new DB tables (pages.quality already exists) New /api/pages/[id]/reprocess route UI changes to DocumentPanel only
Expected Impact
Directly improves data quality, which improves AI analysis reliability. Makes a currently invisible problem visible and actionable.
8

Cross-Case Legal Section Frequency & Risk Analytics

A dashboard view showing which IPC/BNS sections appear most in a case, with direct Concordance Matrix cross-linking
High-Value Medium Complexity
Problem
The legal_sections API and ConcordanceMatrix exist but appear disconnected from actual case data. There is no automated detection of which sections are cited in documents. The LegalSectionsTab in the Case Workspace likely requires manual entry. The concordance matrix's power is not connected to live case analysis.
Proposed Implementation
Add a regex-based section extractor that runs during (or after) OCR, identifying patterns like "Section 302 IPC", "u/s 420", "Sec 187 BNSS" in extracted page text and auto-populating the legal sections table. Add a recharts bar chart to the Case Workspace's Overview tab showing section frequency. Each bar links to the Concordance Matrix pre-filtered on that section. Add a severity indicator using the existing bailable/non-bailable metadata already in lib/legal/sections.ts.
User Benefit
Removes the manual work of identifying which laws apply. Instantly shows whether a case involves predominantly bailable or non-bailable offenses, informing bail strategy.
Tech Required
Regex pattern library (no external dep) Run during document processing pipeline Recharts (already installed) Link to existing Concordance Matrix
Expected Impact
Closes a significant gap between the concordance matrix (static reference) and actual case data (dynamic). Makes the legal section feature genuinely useful rather than decorative.
9

Animated Cause List with Google Calendar / iCal Export

Upgrade the weekly board with drag-and-drop rescheduling and one-click calendar export for upcoming hearings
High-Value Low Complexity
Problem
The Cause List (Court Diary / Roznamcha) is a read-only weekly board. Advocates need to actually attend these hearings — yet there is no way to export them to a calendar, set a reminder, or quickly reschedule a hearing when a date changes. This is a daily-use workflow that is currently not supported.
Proposed Implementation
Add an "Export Week to Calendar" button that generates an .ics file containing all hearings in the current week view. Each calendar event includes the case number, court, judge, and a deep-link back to the case. Add a "Jump to today" button and a month-view toggle. For rescheduling, add a right-click context menu on a hearing card to change the date (fires a PATCH /api/hearings/[id]). Add Framer Motion card-flip animation when switching between week views.
User Benefit
Integrates with advocates' existing calendar workflow. An .ics file works with Google Calendar, Outlook, and Apple Calendar without any API key or OAuth setup.
Tech Required
ics file generation (pure JS, no dep) PATCH /api/hearings/[id] Framer Motion (already installed) No external API needed
Expected Impact
Converts a passive display into an active daily tool. Low complexity for high perceived value in a demo.
10

Progressive Web App (PWA) + Offline Mode

Make NyayaTrace installable and functional offline for court visits where internet is unreliable
Optional Innovation Medium Complexity
Problem
Indian court halls frequently have poor or no internet connectivity. An advocate who has uploaded all documents and run analysis cannot access their case notes or bail calculations from their phone in court. The app is entirely server-dependent (SQLite is local, but the Next.js app itself must run).
Proposed Implementation
Add a next-pwa service worker configuration. Cache the case list, hearing calendar, bail brief pages, and report views in the service worker. Use IndexedDB (via idb) to store a read-only snapshot of selected cases. Add an "Add to Home Screen" prompt. For offline editing, queue changes locally and sync when connectivity returns (only for hearing notes and annotations — not OCR or AI analysis). Show a clear "Offline — cached data" banner.
User Benefit
Advocates can reference their case timeline, bail deadline, and hearing notes from their phone in court, without internet. The app becomes part of the courtroom workflow, not just the office workflow.
Tech Required
next-pwa or @ducanh2912/next-pwa idb (IndexedDB wrapper) Service worker caching strategy manifest.json (icons + theme)
Expected Impact
Strong differentiator for real-world deployment story. Moderate complexity but no new infrastructure required.
Recommended Implementation Roadmap
Phase 1 — Foundation Security, Discovery & Core UX Gaps
#1 Real Authentication: Users table, bcrypt passwords, JWT HttpOnly cookies, middleware auth guard, role-based route protection. This must come first — it unblocks all multi-user scenarios.
#5 Statutory Bail Alerts: Notification bell in Topbar, urgency badges on the sidebar nav item, dismissible alert panel. Builds on existing calculateStatutoryBail with minimal new code.
#6 FTS5 Full-Text Search: Single migration, extended search API, upgraded CommandPalette results with document snippets. Highest ROI relative to effort.
#7 OCR Quality Dashboard: Visual page quality map in DocumentPanel, per-page re-process button. Directly improves data quality for all downstream features.
Estimated effort: 2–3 weeks for a solo developer
Phase 2 — Intelligence & Visualization Make Data Tell a Story
#2 Unified Case Timeline: SVG timeline merging all event types. The most visually impactful single feature. Deploy first on Case Progress page, then add to Case Workspace overlay.
#8 Legal Section Auto-Extraction: Regex extractor during OCR pipeline, section frequency chart, Concordance Matrix deep-linking. Turns two currently isolated features into a connected workflow.
#9 Cause List Calendar Export: .ics generation, right-click reschedule, Framer Motion transitions. Low effort, high daily-use value.
Estimated effort: 2–3 weeks for a solo developer
Phase 3 — AI & Mobility Ambitious Differentiators
#3 AI Draft Generator: /api/cases/[id]/bail-draft/generate, tiptap rich-text editor, template fallback when no AI key, enhanced Word/PDF export. Closes the research-to-filing loop.
#4 Contextual AI Chat: Streaming Gemini/OpenAI chat drawer in Verification Workspace, grounded citations, session-stored conversation. Highest demo wow factor with responsible AI guardrails.
#10 PWA + Offline Mode: Service worker, IndexedDB caching for read views, manifest. Best deployed after all core features are stable.
Estimated effort: 3–4 weeks for a solo developer. Requires Gemini/OpenAI API key for AI features.
